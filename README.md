# price-tag-vision

Сервис извлечения данных с ценников из видео полок магазина.
Загружаешь MP4 — на выходе CSV с распознанными полями по каждому ценнику.

---

## 1. Быстрый запуск (Docker)

### Требования

- Docker и Docker Compose.
- **Желательно GPU NVIDIA** + установленный NVIDIA Container Toolkit на хосте.
  Детектор и трекинг идут на GPU — на CPU всё тоже работает, но в разы
  медленнее. Без GPU достаточно убрать у сервиса `vision-service` ключи
  `gpus: all` и `NVIDIA_*` в `docker-compose.yml`.

### Шаги

```sh
# 1. создать .env из примера (значения по умолчанию рабочие)
cp .env.example .env

# 2. собрать и поднять весь стек
docker compose up --build
```

Готово. Доступы:

- Веб-интерфейс: http://localhost:5173
- Backend API: http://localhost:8000
- Vision-сервис: http://localhost:9001
- MinIO (хранилище артефактов): http://localhost:9002 — логин/пароль `minioadmin` / `minioadmin`

### Как пользоваться

1. Открыть http://localhost:5173
2. Загрузить `.mp4`
3. Дождаться статуса `succeeded`
4. Посмотреть таблицу-превью с распознанным CSV и скачать сам CSV

Ограничение по времени на задачу снято — длинное видео обрабатывается
столько, сколько нужно (полное 4K-видео — это десятки минут).

Остановить: `docker compose down`
Логи: `docker compose logs -f backend worker vision-service`

## 2. Как устроен сервис

### Компоненты

```
Пользователь → Frontend → Backend (FastAPI) → Postgres (метаданные задач)
                                            → Redis + RQ (очередь)
                                                   ↓
                                              Worker → Vision-сервис → MinIO (S3)
                                                                          ↓
                                                            Frontend (превью + CSV)
```

- **Frontend** — загрузка видео, статус, таблица-превью результата, скачивание CSV.
- **Backend** — создание задач, статус, доступ к артефактам.
- **Redis + RQ** — асинхронная очередь задач.
- **Worker** — берёт задачу из очереди и вызывает vision-сервис.
- **Vision-сервис** — выполняет CV/OCR-пайплайн (это «мозг»).
- **MinIO** — хранит входное видео и выходные артефакты (CSV, превью).
- **Postgres** — метаданные и статусы задач.

Каждая задача независима, состояние хранится в Postgres/Redis/MinIO, а не
в памяти процессов.

### Пайплайн обработки (vision-сервис, `price_tag_v5`)

Видео проходит через последовательность стадий:

1. **Сэмплинг кадров** — 5 кадров/сек, коррекция дисторсии объектива и
   поворот в вертикальное рабочее пространство (лучше для детектора и OCR).
2. **Детектор + трекинг** — YOLOv8m находит ценники, ByteTrack ведёт
   каждый ценник как трек между кадрами.
3. **Вырезание кропов** — по каждому треку берутся лучшие по качеству кропы.
4. **Слияние в слоты** — фрагментированные треки одного физического
   ценника объединяются в один стабильный слот (больше данных на один
   ценник → точнее распознавание).
5. **OCR + каталог** — PaddleOCR читает блоки текста; бренд-токены
   сопоставляются со справочником товаров и дают точное название и
   штрихкод. Если уверенного совпадения нет — подставляется ближайшее
   правдоподобное название (поле не остаётся пустым), но штрихкод при
   этом не выдаётся (штрихкод — ключ сопоставления, ошибка тут недопустима).
6. **Сборка строк** — выбор лучшего кадра на ценник, взаимная подстановка
   QR↔видимые поля, вывод цен/скидки, дефолтные значения.
7. **Фильтр и уверенность** — оставляются все локализованные ценники,
   близкие дубликаты схлопываются, по каждой строке считается
   confidence; рядом пишется `debug/row_confidence.json` для триажа.
8. **Запись CSV** — итог в исходной ориентации видео (сырой кадр 3840×2160).

**Результат задачи:**

- `result.csv` — 29 колонок (порядок строго по схеме ТЗ), координаты bbox в системе исходного видео;
- `preview.json` — превью строк CSV (его и показывает фронтенд);
- `debug/row_confidence.json` — уверенность и провенанс по каждой строке.

### Честно про качество

Детектор, трекинг, геометрия и извлечение цен/скидок — корректны и
проверены. Часть полей (`id_sku`, `print_datetime`, `code`, точные копейки,
мелкий шрифт штрихкода) физически не читается на предоставленном дальнем
4K-видео — это ограничение исходных данных по разрешению, а не дефект
пайплайна. Сервис максимизирует то, что реально достижимо: локализацию
ценников, точную идентификацию по каталогу (без ложных штрихкодов) и
confidence для отбора надёжных строк.

## 3. Масштабирование

- **Воркеры — горизонтально.** Все воркеры читают одну Redis-очередь.
  Чтобы обрабатывать больше видео параллельно — добавить реплики сервисов
  `worker` и `vision-service` (например, `docker compose up --scale
  worker=4 --scale vision-service=4`); каждая задача независима.
- **Vision-сервис — без состояния.** Артефакты идут в MinIO/S3, поэтому
  инстансы можно ставить за балансировщик; на каждый инстанс — свой GPU.
- **Backend — без состояния**, состояние задач в Postgres; масштабируется
  репликами за общим Postgres/Redis.
- **Хранилище.** MinIO в проде заменяется на любой S3-совместимый сервис
  (переменные `S3_*` в `.env`).
- **БД/очередь.** Postgres и Redis — управляемые/кластерные в проде.

Узкое место под нагрузкой — GPU vision-сервиса; масштабируется числом
GPU-инстансов, очередь сглаживает пики.

## 4. Прозрачность: модели, данные, железо, требования

### Модели и лицензии (всё работает локально, без облачных API)

| Компонент | Роль | Лицензия |
|---|---|---|
| YOLOv8m (Ultralytics) | детектор ценников | AGPL-3.0 |
| PaddleOCR | OCR (числа/токены) | Apache-2.0 |
| Tesseract (fallback, `rus+eng`) | OCR | Apache-2.0 |
| ByteTrack | трекинг | MIT |

Веса детектора обучены нами и лежат в репозитории
(`runs/detect/train/weights/best.pt`). Сторонние онлайн-OCR/API не
используются — требование локального контура соблюдено.

### Данные и разметка (честно)

- `data/db_hack.csv` — предоставленный справочник соответствия
  `штрихкод → название` (~625k строк, ~356k уникальных кодов, ~136k имён,
  кодировка CP1251). Используется **офлайн, только на чтение** как опора
  идентификации; лежит в репозитории (нужен в рантайме).
- Датасет детектора: 83 кадра / 909 боксов, один класс `price tag`.
  Разметка — **авто-лейблинг детектором + NCC-пропагация бокса между
  соседними кадрами**; ручная разметка на этапе инференса **не
  применяется** (оператор не выбирает кадры, не правит bbox/CSV).

### Железо, на котором тестировалось

| Параметр | Значение |
|---|---|
| Тест-стенд | Windows 11 + NVIDIA RTX 3060 Laptop 6 ГБ |
| GPU | YOLOv8m + ByteTrack |
| CPU | PaddleOCR / резолвер каталога |
| Время обработки | полное предоставленное 4K-видео ≈ десятки минут (узкое место — OCR на CPU; ТЗ допускает, real-time не требуется) |
| Минимум | x86-64 CPU + 8 ГБ ОЗУ + Docker (медленно, OCR на CPU) |
| Рекомендуется | NVIDIA GPU ≥ 6 ГБ + NVIDIA Container Toolkit |

Лимит времени на задачу снят намеренно: длинное видео обрабатывается
полностью, без обрыва по таймауту.

## Локальный прогон пайплайна (без Docker)

Полный прогон по размеченному видео и оценка против ground truth:

```sh
uv run --project vision_service python vision_service/scripts/smoke_price_tag_pipeline.py \
  --video data/videos/26_12-20/26_12-20.mp4 --pipeline price_tag_v5 \
  --output-dir artifacts/run --job-id r1 \
  --sample-fps 5 --max-frames 600 --max-total-crops 900 \
  --max-crops-per-frame 32 --max-candidates-per-frame 32

uv run --project vision_service python vision_service/scripts/eval_price_tag_predictions.py \
  --pred artifacts/run/outputs/r1/result.csv --gt data/videos/26_12-20/26_12-20.csv
```

Сводный MVP-отчёт (recall, точность имени, confidence):

```sh
uv run --project vision_service python tools/v5_mvp_report.py \
  --pred artifacts/run/outputs/r1/result.csv \
  --gt data/videos/26_12-20/26_12-20.csv \
  --side-car artifacts/run/outputs/r1/debug/row_confidence.json
```

## Структура репозитория

- `frontend/` — веб-интерфейс
- `backend/` — API, жизненный цикл задач, доступ к хранилищу
- `vision_service/` — CV/OCR-пайплайн
- `shared/` — общая схема CSV
- `docker-compose.yml` / `.env.example` — всё для локального развёртывания
