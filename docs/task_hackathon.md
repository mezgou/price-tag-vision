# Lenta Tech Life Hack — консолидированный контекст задачи

> Документ собран как рабочая шпаргалка по задаче хакатона: постановка, входные данные, ожидаемый результат, ограничения, критерии оценки, расшифровка полей ценников и уточнения из FAQ/чата.  
> Не заменяет официальный регламент и материалы организаторов, но собирает в одном месте основной контекст, который нужен для проектирования решения.

---

## 1. Краткая суть задачи

Нужно разработать программное решение на базе компьютерного зрения для автоматического распознавания ценников с видео, снятого роботом, движущимся вдоль стеллажей в торговом зале.

Идеальный результат: пользователь загружает видео с робота в интерфейс, система находит на кадрах уникальные ценники, распознаёт из них максимум полезных данных и отдаёт `.csv`, где одна строка соответствует одному уникальному обнаруженному ценнику.

Ключевая цель — не просто OCR текста, а превращение видеопотока в структурированные данные о ценнике: товар, цены, штрихкод/QR, артикул, дата печати, координаты и другие атрибуты.

---

## 2. Бизнес-контекст

Lenta Tech развивает инструменты автоматизации магазина и рассматривает компьютерное зрение как часть цифрового мониторинга торгового зала.

Контроль полки в ретейле нужен, чтобы:

- проверять наличие товара на полке;
- контролировать корректность ценников и их отсутствие;
- ускорять выкладку и реакцию сотрудников;
- повышать качество данных о состоянии полки;
- создавать основу для дальнейшей автоматизации: автозаказ, контроль планограммы, аналитика выкладки.

В текущем кейсе фокус уже не на стационарных камерах, а на мобильном источнике данных — роботе, который проходит вдоль стеллажей и собирает видео по зоне магазина.

## 3. Что нужно сделать

### 3.1. Основной пайплайн

Решение должно:

1. Принимать на вход видео с робота.
2. Анализировать видеопоток и выполнять предобработку.
3. Детектировать ценники на кадрах.
4. Распознавать максимальное количество ключевых параметров на каждом ценнике.
5. Убирать дубли одного и того же ценника, который появляется на нескольких кадрах.
6. Выбирать для каждого уникального ценника кадр/момент с лучшим качеством распознавания.
7. Формировать итоговый `.csv` в требуемом формате.
8. Предоставлять UI, где можно загрузить видео и скачать результат.

### 3.2. Пользовательский интерфейс

Нужен работающий интерфейс, в котором проверяющий может:

- загрузить видео с робота;
- запустить обработку;
- получить/скачать `.csv` с результатами;
- желательно увидеть промежуточные результаты: найденные ценники, bbox, распознанные поля, статус обработки.

Интерфейс можно делать на любом open-source фреймворке. В материалах упоминаются варианты деплоя: Hugging Face Spaces, Render, Vercel, Cloudflare Pages/Workers, Netlify, Firebase, Fly.io, Koyeb, Northflank, Replit и т.д.

### 3.3. Презентация решения

В презентации должны быть:

- титульный слайд с названием решения и команды;
- состав команды: участники, роли, контакты;
- анализ задачи и особенностей входных данных;
- архитектура решения и логика пайплайна;
- примеры работы интерфейса;
- пример выходного датасета/CSV;
- ограничения подхода;
- идеи масштабирования;
- ссылка на репозиторий с исходным кодом;
- подробный `README.md` с архитектурой и инструкцией локального запуска;
- ссылка на задеплоенное решение для демонстрации.

## 4. Входные данные

### 4.1. Формат данных

Организаторы предоставляют набор видеозаписей, полученных с робота в реальных условиях торгового зала. В чате было уточнено, что данные даются именно в формате видео, а разметка к ним предоставляется.

Проверка итогового качества выполняется на private-части/контрольных видео.

### 4.2. Сцены и зоны магазина

Видеоматериалы охватывают разные зоны магазина, например:

- алкогольная продукция;
- молочные товары;
- мёд;
- джемы;
- сиропы;
- другие стеллажи с реальной выкладкой.

### 4.3. Сценарии движения робота

В материалах указаны два сценария:

- **С остановками** — робот фиксируется перед каждой полкой.
- **Без остановок** — робот непрерывно движется вдоль стеллажа.

### 4.4. Особенности съёмки

Ожидаемые сложности:

- смешанное освещение: естественный свет + светильники магазина;
- блики, тени, засветы;
- разная высота расположения ценников;
- разные углы относительно камеры;
- частичное перекрытие ценников товарами или элементами полки;
- съёмка через стеклянное ограждение в некоторых зонах;
- motion blur при движении робота;
- один ценник может попадать в кадр несколько раз и в разном качестве;
- штрихкоды и QR-коды могут быть мелкими или плохо читаемыми.

## 5. Выходной CSV

Каждая строка выходного `.csv` должна соответствовать одному уникальному обнаруженному ценнику на видео.

### 5.1. Поля с ценника

| Поле | Описание |
|---|---|
| `filename` | имя видеофайла |
| `product_name` | наименование товара |
| `price_default` | цена без карты |
| `price_card` | цена по карте |
| `price_discount` | цена по акции |
| `barcode` | штрихкод |
| `discount_amount` | размер скидки |
| `id_sku` | артикул/SKU |
| `print_datetime` | дата и время печати ценника |
| `code` | код зоны выкладки |
| `additional_info` | дополнительная информация с ценника |
| `color` | цвет ценника |
| `special_symbols` | тип выкладки / специальные символы |
| `frame_timestamp` | время в миллисекундах от начала видео, на котором зафиксирован ценник |
| `x_min` | x-координата левого верхнего угла bbox, пиксели |
| `y_min` | y-координата левого верхнего угла bbox, пиксели |
| `x_max` | x-координата правого нижнего угла bbox, пиксели |
| `y_max` | y-координата правого нижнего угла bbox, пиксели |

### 5.2. Поля из QR-кода

| Поле | Описание | Поле в QR |
|---|---|---|
| `qr_code_barcode` | штрихкод из QR | `barcode` / `b` |
| `price1_qr` | цена 1 | `price1` / `p1` |
| `price2_qr` | цена 2 | `price2` / `p2` |
| `price3_qr` | цена 3 | `price3` / `p3` |
| `price4_qr` | цена 4 | `price4` / `p4` |
| `wholesale_level_1_count` | оптовый порог 1, количество товара | `wholesaleLevel1Count` / `wL1C` |
| `wholesale_level_1_price` | оптовый порог 1, цена | `wholesaleLevel1Price` / `wL1P` |
| `wholesale_level_2_count` | оптовый порог 2, количество товара | `wholesaleLevel2Count` / `wL2C` |
| `wholesale_level_2_price` | оптовый порог 2, цена | `wholesaleLevel2Price` / `wL2P` |
| `action_price_qr` | акционная цена | `actionPrice` / `aP` |
| `action_code_qr` | код акции | `actionCode` / `aC` |

### 5.3. Полный заголовок CSV

```csv
filename,product_name,price_default,price_card,price_discount,barcode,discount_amount,id_sku,print_datetime,code,additional_info,color,special_symbols,frame_timestamp,x_min,y_min,x_max,y_max,qr_code_barcode,price1_qr,price2_qr,price3_qr,price4_qr,wholesale_level_1_count,wholesale_level_1_price,wholesale_level_2_count,wholesale_level_2_price,action_price_qr,action_code_qr
```

### 5.4. Правила заполнения полей

- Если параметр **отсутствует на конкретном ценнике**, в поле нужно написать `нет`.
- Если параметр **есть, но не распознан**, поле нужно оставить пустым.
- Если штрихкод распознан частично, например 12 цифр из 13, лучше записать распознанные 12 цифр, чем не передавать поле совсем.
- Название товара не обязано совпадать символ-в-символ, но чем ближе к фактическому тексту, тем лучше.
- `frame_timestamp` указывается в миллисекундах от начала видео.
- Для `frame_timestamp` и bbox лучше выбирать момент/кадр с лучшим качеством распознавания конкретного ценника.
- В чате было уточнено, что CSV должен быть в стандартном формате: разделитель `,`, десятичный разделитель `.`, кодировка UTF-8; строковые поля обрамлять двойными кавычками, если внутри есть запятые или кавычки.

## 6. Как будет сопоставляться результат с ground truth

Из уточнений организаторов:

1. **Приоритетный ключ сопоставления — `barcode`.**  
   Если штрихкод распознан и он есть в ground truth, строка может сопоставляться напрямую по нему.

2. **Второй ключ — пространственно-временной:** `frame_timestamp` + bbox (`x_min`, `y_min`, `x_max`, `y_max`).  
   Он используется, если штрихкод не распознан или отсутствует в ground truth.

3. Если строку нельзя сопоставить ни по `barcode`, ни по пространственно-временному ключу, она может не засчитаться как правильный ценник.

4. Если сопоставление удалось, дальше оценивается качество распознавания содержательных полей.

5. По bbox и timestamp должны использоваться допуски. Организаторы писали, что если выбрать любой кадр из интервала, где ценник виден хорошо, это почти наверняка попадёт в допуски.

6. Bounding box в FAQ был описан как техническое поле/ключ, а не главный содержательный критерий. Основной фокус — качество распознавания данных с ценника.

## 7. Критерии успешного решения

Официально успешное решение должно:

1. Корректно распознавать ценники на видео.
2. Извлекать максимальное количество ключевых параметров.
3. Выдавать результат в понятном структурированном `.csv`.
4. Иметь работающий UI для загрузки видео и скачивания CSV.
5. Демонстрировать разумную архитектуру.
6. Работать в локальном контуре без внешних онлайн-сервисов.
7. Быть масштабируемым под разные типы стеллажей и форматы ценников.
8. По возможности быть применимым на ограниченных вычислительных ресурсах.

Официальная метрика: доля ценников с контрольного видео, для которых точность распознавания составляет не менее 80%, от общего числа ценников.

На финале дополнительно оцениваются защита и презентация решения.

## 8. Приоритеты распознавания

По уточнениям с чекпоинта и FAQ:

### Самое важное

- содержательные поля, которые позволяют понять, какой товар находится на ценнике и какая у него цена;
- поля, которые позволяют связать ценник с товаром: `product_name`, `barcode`, `id_sku`, цены;
- стабильное распознавание по реальным плохим кадрам, а не только на красивых crop'ах.

### QR-код

- QR-код распознавать полезно, но это не абсолютно критичный блок.
- Организаторы понимают, что из-за качества изображений и разрешения камеры QR может распознаваться не у всех и не всегда.
- Отсутствие распознавания QR само по себе не должно быть критическим минусом.
- Можно сфокусироваться на содержательных полях ценника и извлекать максимум доступной информации без QR.

### Штрихкод

- Barcode важен как первичный ключ сопоставления с ground truth.
- Даже частично распознанный barcode лучше, чем пустое поле.

### Название товара

- Не обязательно идеально символ-в-символ.
- Чем ближе к фактическому тексту на ценнике, тем лучше.
- Нормализация регистра, лишних пробелов, OCR-ошибок и сокращений может быть полезной.

## 9. Ограничения и разрешённые подходы

### 9.1. Разрешено

- Любые методы детекции объектов и OCR, а также их комбинации.
- Готовые модели и библиотеки, если они могут быть развернуты локально.
- Предобученные модели с открытыми лицензиями, допускающими нужное использование.
- Внешние открытые источники данных, если они не требуют обращения к недоступным API и имеют понятный источник/лицензию.
- Собственная база SKU/товаров, собранная командой.
- Дообучение моделей на дополнительно собранных данных.
- Ручная разметка только как часть подготовки обучающих данных или дообучения, при прозрачном описании: что размечали, в каком объёме, откуда данные, как использовали.

### 9.2. Запрещено или нежелательно

- Внешние онлайн-сервисы, облачные OCR/API и инструменты, которые нельзя воспроизвести в контуре компании.
- Ручная корректировка результата в финальном решении.
- Участие оператора на инференсе: выбор кадров, правка bbox, подтверждение OCR, ручная правка CSV и т.п.
- Непрозрачное использование внешних данных/весов/датасетов.
- Избыточно тяжёлые модели без объяснения применимости.

### 9.3. Локальный контур и железо

- Решение должно быть воспроизводимо локально.
- Запуск именно на роботе не является обязательным требованием.
- Приоритет — обычное десктопное решение.
- Распределённая архитектура, обработка на роботе или оптимизация под робота могут быть плюсом, но не являются обязательными.
- Оптимизация под `rknn` / `int8` приветствуется.
- Точные ограничения по железу не фиксировались; организаторы просили не привязывать решение к конкретной конфигурации.
- В `README.md` стоит указать, на каком железе тестировалось решение, примерное время обработки, минимальные и рекомендуемые требования.

## 10. Скорость обработки

Уточнения из FAQ:

- Строгого требования real-time нет.
- Жёсткого ограничения по FPS нет.
- Время обработки не является основной метрикой.
- Главный приоритет — точность распознавания и качество итогового CSV.
- Хороший ориентир — несколько секунд на обработку кадра, но более долгие варианты допустимы, если есть качество и понятная архитектура.
- Если обработка одного ролика занимает очень много времени, это может быть минусом с точки зрения практической применимости, архитектуры и масштабируемости.

Практический вывод: сначала обеспечить качество и устойчивость, затем оптимизировать скорость, кэширование, выбор кадров, батчинг и требования к ресурсам.

## 11. Материалы по ценникам

### 11.1. `Расшифровка ценники.pptx`

Это основной прикладной материал для текущей задачи. В нём показаны 7 типов ценников и расшифрованы поля, которые важно распознавать.

Повторяющиеся поля в этих 7 типах:

- полное название товара;
- размер скидки от цены без карты;
- QR-код;
- цена за единицу без карты;
- цена по карте / цена за единицу по карте;
- цена за единицу по акции;
- `id_sku`;
- полная дата и время печати ценника;
- штрихкод, цифры;
- код зоны выкладки;
- тип выкладки;
- дополнительная информация;
- шелфтокер.

Для типа с шелфтокером в примерах указано, что там может быть дополнительная информация по товару, например номер на весах, «Удачная упаковка» и т.п.

### 11.2. `ГМ для ТК.pptx`

Это расширенный справочный материал по вариантам ценников в гипермаркетах Ленты. Его задача — показать разнообразие макетов, а не только точную расшифровку текущих полей.

В нём встречаются:

- разные размеры: `6x6`, `6x12`, `A5`, `A4`, `A3`, `A2`, `МНЦ`;
- вертикальные и горизонтальные форматы;
- регулярные ценники / РПЦ;
- акционные ценники / АПЦ;
- распродажа;
- скидка при покупке;
- скидка от/до N штук;
- BOGOF;
- детские ценники;
- весовые ценники за `1 кг` и `100 г`;
- ценники за `1 шт`;
- варианты с номером кнопки на весах и без него;
- ТОП/СТОЛОТО;
- варианты с шелфтокером;
- разные цвета, включая красные, жёлтые, зелёные, белые и др.

Тип выкладки может выводиться на ценник, если значение есть в системе. В справочнике указаны обозначения:

- `ш` — штуки;
- `л` — лоток;
- `к` — короб.

Для части акционных A-форматов есть правило отображения скидки: если скидка в рублях меньше 100 рублей, она отображается в процентах; если больше или равна 100 рублей — в рублях.

Для текущей задачи организаторы отдельно уточняли: в первую очередь ориентироваться на `Расшифровка ценники.pptx` и предоставленные данные; `ГМ для ТК.pptx` использовать как дополнительный справочник для понимания вариативности и масштабирования.

## 12. Рекомендуемая инженерная стратегия

Это не официальное требование, а практическая интерпретация задачи.

### 12.1. Базовый пайплайн

1. **Frame sampling**  
   Выбирать кадры из видео с разумной частотой: чаще на быстрых фрагментах, реже на остановках.

2. **Детекция ценников**  
   Использовать object detection/segmentation для нахождения ценников. Можно стартовать с YOLO/RT-DETR/Detectron-подобных моделей или классических методов + OCR proposals.

3. **Tracking / de-duplication**  
   Связывать один и тот же ценник между кадрами, чтобы не писать дубликаты в CSV.

4. **Best-frame selection**  
   Для каждого track выбирать кадр с наилучшей читаемостью: крупный bbox, резкость, минимальные блики, фронтальный угол, минимальное перекрытие.

5. **Crop + rectification**  
   Вырезать ценник, исправлять перспективу, повышать резкость/контраст, при необходимости увеличивать разрешение crop'а.

6. **Template/type classification**  
   Определять тип ценника или хотя бы семейство шаблона, чтобы понимать, где искать название, цены, штрихкод, дату, id_sku.

7. **OCR и парсинг полей**  
   Распознавать текст и цены, затем постпроцессить регулярками, словарями, SKU-базой и правилами шаблонов.

8. **Barcode/QR detection**  
   Пробовать считывать штрихкод и QR из crop'а и/или из увеличенного участка. При неуспехе оставлять поле пустым или частично заполненным.

9. **Aggregation across frames**  
   Объединять несколько OCR-попыток с разных кадров: голосование, confidence, выбор наиболее правдоподобного значения.

10. **CSV export**  
   Приводить всё к требуемому формату, проверять заголовки, порядок колонок, кодировку, пустые значения и `нет`.

### 12.2. Что особенно улучшает качество

- Использовать несколько кадров одного ценника, а не один случайный crop.
- Выбирать кадр с максимальной читаемостью, а не первый кадр появления.
- Отдельно распознавать зоны: название, цена, barcode, дата, `id_sku`.
- Использовать шаблоны ценников для локализации полей.
- Нормализовать цены: `99 90`, `99,90`, `99.90`, `99-90` → единый формат.
- Нормализовать даты и время печати.
- Использовать внешний/самостоятельно собранный справочник SKU/товаров для исправления OCR по названию.
- Валидировать barcode по длине/цифрам/контрольной сумме, но не выкидывать частичный результат.
- Хранить confidence по каждому полю и использовать его при агрегации.

## 13. FAQ и важные уточнения с чекпоинта

### 13.1. Десктоп или робот

Приоритет — обычное десктопное решение. Запуск на роботе, распределённая архитектура или обработка прямо на роботе могут быть плюсом, но не обязательны.

### 13.2. Real-time

Строгого требования к real-time нет. Чем быстрее, тем лучше, но важнее качество и применимость.

### 13.3. Допустимое время обработки

Не нужно упираться только в скорость. Если обработка занимает больше времени, это не автоматический провал. Важно объяснить, как решение будет масштабироваться и применяться в бизнес-процессе.

### 13.4. QR-код

QR распознавать не обязательно любой ценой. Из-за качества изображений он может не читаться. Отсутствие QR само по себе не критично, если распознаются остальные содержательные поля.

### 13.5. Можно ли отказаться от QR

Да, можно сфокусироваться на содержательных полях ценника и извлекать максимум доступной информации из остальных элементов.

### 13.6. Самые важные поля

Приоритет — поля, которые помогают понять, какой товар на ценнике и какая у него цена, а также поля для связи ценника с товаром.

### 13.7. Неполный barcode

Если удалось распознать 12 цифр из 13, нужно передать 12 цифр, а не оставлять поле пустым.

### 13.8. Название товара

Название не обязано быть символ-в-символ, но близость к фактическому тексту повышает качество.

### 13.9. Bounding box

Bbox используется как техническое поле/ключ и не является главным содержательным полем оценки. Основной фокус — распознавание данных с ценника.

### 13.10. Внешние источники и SKU-базы

Можно использовать внешние открытые источники, собственно собранные базы SKU/товаров, данные сайта и другие подходы, если это помогает распознаванию и не нарушает условия локального воспроизведения и лицензий.

### 13.11. Дообучение на дополнительных данных

Можно собирать дополнительные данные и дообучать модели. Итоговое решение должно работать автономно, без ручного вмешательства.

### 13.12. Ручная разметка

Ручная разметка допустима только как часть подготовки обучающих данных или дообучения. На этапе инференса нельзя вручную размечать, корректировать результат, выбирать кадры или править CSV.

Если ручная разметка использовалась, нужно честно описать:

- какие данные размечались;
- откуда они взяты;
- какой объём разметки выполнен;
- какие модели дообучались;
- как данные использовались в пайплайне.

### 13.13. Деплой и доступы

Если для проверки решения нужен логин, пароль или другой способ доступа, нужно явно указать все данные и инструкции для проверяющих. Главное — чтобы работу решения можно было воспроизвести.

### 13.14. Если никто не достигнет порога качества

Оценка будет проводиться по фактическим результатам решений. Нужно стремиться к максимальному качеству и объяснять сильные стороны подхода.

## 15. Риски задачи

- Низкое разрешение crop'ов ценников.
- Мелкие QR/barcode, которые плохо читаются.
- Блики и стекло.
- Перспективные искажения.
- Motion blur.
- Частичные перекрытия.
- Несовершенная исходная разметка: в чате отмечалось, что bbox могут быть неидеальными.
- Разнообразие шаблонов, размеров, цветов и механик ценников.
- Необходимость удалить дубли одного ценника на разных кадрах.
- Возможное расхождение форматов в предоставленной разметке и ожидаемом CSV, поэтому нужен собственный валидатор.

## 18. Короткий summary для команды

Нужно сделать не просто OCR, а end-to-end систему: видео → уникальные ценники → структурированный CSV. Самое важное — качество распознавания товарных и ценовых полей. QR полезен, но не критичен. Barcode очень важен как ключ сопоставления. Bbox/timestamp нужны как технический ключ и должны указывать на хороший кадр. Финальное решение должно быть автоматическим, локально воспроизводимым, без внешних облачных API. Десктопное решение достаточно; запуск на роботе — бонус. Скорость важна, но вторична относительно точности и практической архитектуры.
